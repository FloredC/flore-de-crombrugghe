Project snapshots — building a third content tier

Sinomocene, Teamchatviz and the Roche Icon System: three short project pages that are deliberately not case studies. Mostly a story about how much of a design system you can only discover by building the third instance of it — and about the difference between a rule that holds and a rule that has only been tested twice.

26 Aug 2026 Three pages, one layout, and the assumption that lasted a day Building with Claude

The two full case studies (PitchPivot, Artifakt) were built. This session added the tier below them: three short project pages with their own register, sharing one layout component. I designed each frame in Figma first and handed them over one at a time, which turned out to matter — the three diverged in ways nobody would have predicted from the first one.

Where the work started
scope
Designed each frame in Figma first, rather than having Claude propose layouts from the content
Claude laid out both options with trade-offs and leaned the other way — the content brief was prescriptive enough that a code proposal would have been faster, and it offered 2–3 treatments to pick from by eye. Designing first won anyway, and the session justified it: the three frames ended up differing on stage colour, button variant, corner radius, which sections carry titles, and whether a row holds one item or two. A code proposal would have produced three identical pages and I'd have spent the session arguing them apart.
tier
Defined the tier by register, not by length
From the content brief: snapshots are "descriptive, not reflective. State what it is, what was formally difficult, what it deliberately doesn't do. No 'the turning point was' — that register belongs to the three real case studies, and reserving it is what makes the tiering legible." That constraint is now written into the top of the content files as a rule for future edits, not just a description of today's copy — if a snapshot ever grows a Turning Point section, the tier has collapsed and the case studies above it lose their meaning.
layout
One component for all three pages, with nothing keyed on the project slug
PitchPivot and Artifakt each have their own layout file, because their Figma frames genuinely differ in composition. The snapshots are the opposite case: three structurally identical pages that differ only in content, and that sameness is the tier. So anything that varies has to arrive as data. Adding Sinomocene and Roche after Teamchatviz was one registry line plus one content file each.
layout
Opted the tier out of the case-study system's width-alternation rule
The case-study pages enforce "no two consecutive blocks share a width" — the alternation is what gives a long argued page its rhythm, and it's checked at runtime in dev. A snapshot's rows are the same width three times running on purpose: it's a catalogue, not an argument, and varying the widths would imply one view matters more than another. Noted explicitly in the code rather than silently skipped, because "the check isn't running" and "the check doesn't apply" look identical from outside.
What didn't survive contact with the third page

This is the part worth remembering. Two designs are enough to see a pattern and not enough to know it's real.

props
Built one "tone" switch controlling both text colour and button style — and had to split it a day later
Sinomocene's hero is dark, so tone=dark set white text and the outlined button together. The reasoning was defensive: keeping them bundled meant nobody could later pick white text with a dark button on a dark stage and ship an unreadable hero. Then Roche arrived — a light stage with an outlined button, a combination the bundled version literally could not express. The safety concern was real but was being solved in the wrong place; it now lives where it belongs, on the button itself. The generalisation was drawn from two examples and broke on the third.
chrome
Image framing changed three times in one session: shadow → shadow+radius on Roche → grey border everywhere
The last change is the interesting one, and it came from me rather than the build: the drop shadow read as an interaction state. Cards and buttons elsewhere on the site use elevation for hover and selected, so a permanently-raised screenshot looked either clickable or already chosen. A 1px hairline bounds the image without claiming it's interactive. Recorded in the code so nobody re-adds elevation later without meeting the reason.
chrome
Kept three genuinely different treatments rather than normalising them
Teamchatviz's supporting image stays completely bare (it's loose transparent artwork — a box would frame nothing), Sinomocene's legend takes the border with square corners, Roche runs radius 16 where the other two run 12. Each was read off the file and each is deliberate. The temptation to unify all three into one number would have quietly overruled three design decisions.
What I learned about how I structure the Figma file

Meta-knowledge, not product decisions — the stuff that's easy to forget by the next project. Each of these cost a round-trip this session.

What happenedCost, and what to do next time
Hero slots held a placeholder from another project All three frames had the Teamchatviz People Land screenshot sitting in the hero, including on Sinomocene and Roche. Twice this read as "the hero is designed" when the asset didn't exist yet, and both times it surfaced only after the page was built. Next time: leave the slot genuinely empty, or fill it with the real asset. A placeholder from a different project is indistinguishable from a decision.
Layer names weren't updated when fills were swapped Every image on all three pages was still named 01-channel-heartbeat-teamchatviz-screenshot…, including the Roche icon plates. Mapping images to captions had to be done from the rendered screenshot instead of the layer list, which is slower and easier to get wrong. Next time: rename on swap, or accept that the mapping has to be confirmed visually.
Duplicating a row duplicated its caption Happened twice. Teamchatviz row one had Channel Land's caption under the People Land image; Roche's second row still has the same "Base forms" caption under both plates. Both were caught by reading the copy against the brief, not by looking at the page. Next time: when a row is duplicated, the caption is the field to check first — the image gets swapped and the text gets forgotten.
Hidden layers to omit a section — this worked well Sinomocene and Roche hide the What-section title rather than deleting it, and hide row titles on the untitled rows. Unambiguous to read, and it keeps the frames structurally parallel so one layout can serve all three. Worth keeping as a habit.
Bound variables paid off; raw hex didn't Almost everything resolved to a real token, which meant the code could reference the token rather than copy a colour. The two exceptions cost time: the hero greys were raw hex until they got named, and a scaled instance produced a 0.406px border that had to be recognised as a scaling artifact rather than a design value.
Housekeeping that adds noise Every snapshot frame carries two stacked NavbarDesktop instances and a stray empty 1014×162 container. Harmless — the nav is built from code — but they're the kind of thing that makes the next read of the file slower.
Verifying by measuring, not by reading the code back
verify
A claim written in a code comment turned out to be false, and only measuring caught it
The Teamchatviz hero was rendering with no frame at all, because a comment asserted the export had a drop shadow baked into the PNG and that adding a corner radius would clip it. Measured: the file is 99.7% fully opaque with 0% transparent pixels — there is no soft surround at all. The claim was true of the first hero export (the one with the Slack badge) and was never rechecked when it was replaced. A confident comment is not evidence.
verify
Browser measurement caught three things a code read would have passed
Sinomocene's legend was missing a drop shadow the file specified; Teamchatviz's icons were rendering at the component's default radius 24 instead of square; and a first attempt at measuring image quality reported catastrophic errors that turned out to be an artifact of comparing transparent pixels rather than what a viewer sees. All three looked correct in the source.
verify
Checked the video's real dimensions instead of trusting the design's placeholder box
The frame draws a 1283×596 rectangle (2.15:1) labelled "Video embed". The actual video is plain 16:9, so reserving the box at the drawn ratio would have letterboxed the player inside its own rounded frame. Also surfaced that the caption described a 42-minute piece while the embed runs 5:02 — resolved by calling it an excerpt rather than changing the number, since the 42 minutes is a true fact about the work.
assets
Verified duplicate images by checksum rather than by filename or file size
Both the Sinomocene and Roche heroes are byte-identical copies of images already used further down their own pages — confirmed by SHA-256, which is the only check that distinguishes "same picture" from "similar picture, coincidentally similar size". Still open as a design question rather than a bug: each page currently shows the same image twice.
Smaller decisions worth keeping
copy
Inline bold represented as **markers** in the content strings
The bold runs are mid-sentence, not whole paragraphs, so a per-paragraph flag couldn't express them. The tidier alternative — an array of {text, bold} segments — shatters a sentence into a dozen fragments, which makes proofreading the copy against Figma genuinely hard and lets a typo hide at a segment boundary. Markers keep each paragraph one legible string, and render as real <strong> so screen readers get the emphasis too.
privacy
Vimeo embed carries the Do Not Track parameter
The site has no cookie banner, so an embed that quietly starts setting tracking cookies would be a consent problem the page has no way to answer. dnt=1 keeps it a plain video player.
process
Merged the main branch into the working branch before building
The branch was ten commits behind, including a whole responsiveness pass that changed the hero spacing and added the layout constants the new pages sit inside. Building first would have meant building against a stale system and redoing it. Worth checking at the start of a session, not when something looks wrong.

Shareable hook
I built a design system rule from two examples and it broke on the third — within a day. Two of my project pages had a dark background with an outlined button, so I bundled "dark" and "outlined" into a single setting, reasoning they always travel together. Then the third page turned up light-with-outlined: a combination my own abstraction couldn't express. The instinct to prevent a bad combination was right. Encoding it as "these two things are the same decision" was not.
