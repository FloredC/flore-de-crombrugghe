Scroll reveal motion

The brief was loose on purpose: “modern, increases curiosity, but shouldn’t move too much.” I wanted ideas before implementation so I could work structurally instead of approving one effect at a time. What came back was a sandbox of six live experiments running on the site’s own tokens and typeface — and the useful part turned out not to be picking a favourite, but discovering that “shouldn’t move too much” is a number, and that the riskiest part of a scroll reveal has nothing to do with how it looks.

Deciding structurally: three questions, in order

1 · The unit

What counts as one thing arriving — a whole section, the blocks inside it, or the items inside those. This decides how the page feels; everything else is tuning.

2 · The gesture

How it moves. “Shouldn’t move too much” resolved to a dial: 12px of travel reads as arrival, 20px starts to read as performance.

3 · The trigger

One-shot on entry, or mapped continuously to scroll position so it has no moment at all. These feel genuinely different.

The experiments

Six lanes, scrolled the way a visitor would, with live dials for distance / duration / stagger / easing that printed the resulting CSS. Building it rather than describing it was the right call — I can’t judge 12px of movement from a sentence, and the two lanes I ended up rejecting were ones that sounded fine written down.

E3 is the one worth keeping hold of. It’s the only lane whose motion is specific to this site rather than borrowable from any other — and it adds no new animation at all. The avatar already lifts its arm once per 7-second idle loop; that gesture just sits at ~70% of the loop, so left alone it happens about five seconds after the reader has moved on. A negative animation-delay starts the loop shortly before its own gesture, so the avatar performs a movement it already had at the moment the bubble arrives. Nothing to keep in sync, and no conflict with the loop it’s borrowing from.

Decisions

Architecture
The resting state is the finished state. JS arms the hidden state; the stylesheet never hides anything on its own.
The standard recipe puts opacity: 0 in the CSS and has JavaScript remove it — so a failed observer, a JS error or a 404’d bundle leaves a blank page. Inverted: index.html sets data-reveal-armed on <html> before first paint, and every hidden rule is nested under it. This is the same principle the Rega avatar already states in its own comment — nothing has to run for it to look right — applied to the one feature that breaks it by default. Chosen first because retrofitting it means touching every reveal.
Coverage
E3 on every Guide — case studies included, not just the homepage.
I hedged on this initially, on the theory that long-form reading makes repeated motion a tic. Wrong twice: the count was wrong (Artifakt has five Guides, not three), and the density is the opposite of what I assumed — see the measurement below. There was also a precedent I should have led with: AvatarNote renders the same avatar and the same SpeechBubble as the homepage, and I’d already ruled once, on buttons, that one component carries identical states wherever it appears.
Observers
One observer per group, not per element.
A homepage section reveals its wayfinding row, its Guide and six cards — nine observers for what is, in the design, one event. It’s also what makes the stagger possible at all: the items have to share one start time and separate themselves with transition-delay, which can’t work if each waits for its own intersection.
Threshold
IntersectionObserver threshold 0, not a fraction.
The obvious 0.2 means “one fifth visible”, which a block taller than the viewport can never satisfy — a 5000px case-study section peaks at 0.18 in a 900px window and would stay at opacity 0 permanently. Case-study sections are exactly that tall. Threshold 0 plus a bottom margin means “the top edge has come up past this line”, which is true regardless of height.
Markup
Nothing gets wrapped. Reveal marks a container that already exists.
The obvious shape is one <Reveal> per animated thing, which doesn’t survive this codebase: the items are already grid children, flex children and section headings, so wrapping each one puts a div between a grid and its item and breaks the layout it was meant to decorate. Cards index themselves via CSS nth-child, so ProjectCard needed no motion props at all.
Long-form
Case-study prose moves 8px with no stagger; homepage moves 12px with an 80ms stagger.
Browsing benefits from sequence — it says what to look at first. Reading doesn’t. A side effect worth noting: with the stagger at zero, blocks share a start time anyway, so case-study sections need no per-block markup — adding a section to a case study requires no motion code.
Deferred
E5 (scroll-linked) not shipped, despite scoring best on “modern, barely moves”.
Case-study pages already run a rAF scroll pass for the chapter nav and progress line; adding a second continuous loop to a long, image-heavy page is real cost, and reversibility could fight the chapter nav’s own scroll behaviour. Worth revisiting via native animation-timeline: view(), which is one CSS line and no JS at all.

The measurement that reversed my instinct

I nearly left the Guide animation off the case studies because long pages “would feel repetitive”. Measured against a 900px viewport, the gap between neighbouring Guides is:

The long-form pages are where the Guides are most spread out. The homepage is the only place a pair sits comfortably inside one screen — so if the effect ever reads as repetitive it will be there, in exactly the spot I was most confident about. The intuition was not just wrong, it was pointed at the wrong page.

Technical difficulties

A cascade collision, caught in the sandbox before it shipped. One lane faded in correctly but stayed stuck 42px below where it belonged, permanently. Its variant override sat at specificity (0,5,0) while the “visible” rule sat at (0,3,0), so the hidden state kept winning after reveal. Invisible in the source; obvious the moment computed styles were measured. The fix became the rule for the whole system: key the hidden state on the absence of the revealed attribute (:not([data-reveal-in])) and write no matching “visible” rule at all — then a variant can be as specific as it likes and still stop applying the moment the group reveals.

A component that silently swallows refs. Using Reveal as={Container} looked clean and would have left the Contact section invisible forever — Container takes only children, className and id by design and forwards no ref, so the observer would never have attached. React warned about it; the fix was to nest rather than substitute. A good argument for the arming inversion above: even this failure mode degrades to a visible page rather than a blank one.

Reduced motion only works if it lands later in the stylesheet. The override has the same specificity as the rule it’s overriding, so it wins purely on source order. Verified by byte offset in the built CSS rather than assumed. Had Tailwind emitted them the other way round, reduced-motion users would have got the full animation and nothing would have looked wrong in the code.

Verification meta-lesson, worth more than the fixes. The preview browser was throttled — transitions didn’t advance, screenshots came back blank, scrolling timed out — so “watch it animate” wasn’t available. Two probes gave confidently wrong answers before this was noticed: getComputedStyle returns a live object, so a “before” and an “after” snapshot were reading the same current values; and Tailwind escapes its selectors, so searching the CSSOM for 1.04 can never match 1\.04. What worked: inject * { transition: none !important }, toggle the state, and read the resolved cascade instead of trying to catch a frame. When the environment can’t animate, verify the cascade, not the animation.

Working-process note: two dev servers on one port

The session ended with the site apparently missing every change — which turned out to be two Vite instances both claiming port 5173 (one bound to IPv4, one to IPv6), plus a new branch accidentally cut from the commit the day started at rather than from main. Nothing was lost. But the honest lesson is that [vite] Failed to reload errors had been appearing in the console for hours and were repeatedly written off as a stale buffer, because the code kept verifying as correct by other means. Being right about the symptom is not the same as being right about the cause.

What I’d do differently

  • Measure before forming the design opinion, not after being challenged on it. The Guide-density numbers took two minutes and reversed the recommendation.
  • Check for a stray dev server before debugging anything that “isn’t updating” — one lsof would have saved an hour of misattributed console noise.
  • When branching for new work, branch from main explicitly rather than from whatever is checked out.
