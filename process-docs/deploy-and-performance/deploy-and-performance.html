5 Aug 2026 First deploy, and the class of bug dev can't show you Building with Claude

The site had no deployment setup at all — no workflow, no base path, no SPA fallback. Setting that up surfaced a bug that had been sitting in the repo for days, invisible to every check we'd run, because the only environment that could reveal it didn't exist yet.

deploy
Deep links to case studies would have 404'd in production — only the homepage worked
GitHub Pages only serves files that physically exist, and /work/artifakt exists only inside the JS router. Opening, refreshing, or sharing a case-study link would have hit GitHub's 404. Fixed with a 404.html that re-encodes the path into a query, which an inline snippet in index.html restores before React Router boots. Worth naming because nobody would have found this by testing locally — the dev server happily serves every route.
deploy
Five project thumbnails were already broken, and nothing could have shown it
Vite rewrites asset URLs it can see — imports, CSS url(). It cannot see a path that arrives as a string from MDX frontmatter, so /images/… stayed root-absolute: correct on localhost, wrong under /flore-de-crombrugghe/. 21 paths affected. Fixed at render time with assetUrl.js so the .mdx files stay portable and the deploy path lives in one place.
deploy
Applied base to the build only, keeping npm run dev at the root
Daily work stays unchanged rather than requiring a subpath every time. The explicit cost: a base-path bug then cannot appear in dev — which is precisely how the thumbnails got that far. Accepted knowingly, and paid for by committing a Pages simulator (npm run preview:pages) that serves the built site the way Pages actually serves it. That harness was the only thing that found the bug.
perf
Images were 4–5× larger than they render — 14.1MB down to 4.4MB
Everything was exported from Figma at 4x (5x for the About images): 1600px into a 320px slot, 3608px into an 880px one. Retina tops out at 2x, and cost scales with area, so those were 4–6× more pixels than any display can show. Resized to exactly 2× the measured render width — verified every image now resolves at exactly 2.00 natural px per CSS px, so there is no visible change. Plus loading="lazy" on all 20 content images, none of which are above the fold.
perf
Did not ask Flore to re-export anything
Downscaling only ever discards pixels, so Figma stays the source and git history keeps the originals. The export habit doesn't need to change at all — the resize is a committed script with per-image targets, re-runnable if a card's layout width changes.
tokens
Repaired --white-transparent, which had exported with its alpha dropped
It emitted opaque #ffffff, making a "transparent white" token identical to --white. Both badges silently worked around it with a literal bg-white/[0.33] — so the token's value lived as a copy in two component files, the exact drift the token layer exists to prevent. Read the real value back from Figma (#ffffff54 = 32.9%) rather than trusting the workaround. Second export bug of this kind, after the underscore/hyphen mismatch in July.
meta
Added link-preview metadata, which had been deferred as post-validation work
That deferral was decided when nothing was shareable. The moment the site had a public URL about to be sent to design managers, a link unfurling as a bare URL became a real cost. og:image is deliberately left commented out until a 1200×630 asset exists — pointing a preview at a 404 is worse than having none, because some platforms cache the failure.
Meta-learning about the working process: three separate bugs this session shared one shape — the code read correctly, and the only thing that could disprove it was running the artefact the way it would really be run. Reading classes, reading config, and reasoning about the CSS cascade all said "fine." The browser said otherwise. The generalisable version: when a value is composed rather than declared — a base path prefixed at build time, a custom property inside a shorthand, an alpha channel inside a hex — reading the source is not verification.
What I'd do differently next time: set up deployment on day one, before any content or layout work, even with a placeholder page. Not because deploying early is virtuous, but because the deployed environment is a test instrument. Without it we had no way to detect an entire category of bug, and accumulated 21 broken paths without a single failing signal.
Visuals for this section would help — the broken-thumbnail state under the real base path, and a before/after of the network panel showing the image payload drop. Screenshots were taken in-session but pasted into chat rather than saved; drop them into assets/ and they can be wired in.
Shareable hook
Deploying my portfolio revealed five broken images that had been broken for days. Not a regression — they had never worked in production, and nothing could have told me: the paths came from content files, so the build tool never saw them, and the dev server serves from the root where they happen to resolve. The bug wasn't in the code. It was in the fact that the only environment that disagreed with my code didn't exist yet.
26 Aug 2026 The second image pass: format, not just size Building with Claude

The 5 Aug pass resized every image to 2× its render width and stopped there — it never changed format, and three projects' worth of assets arrived after it. Revisiting the whole site cut the built output from 106MB to 47MB. Mostly a story about where the weight actually was, which was not where I'd have guessed.

perf
Converted the site to WebP — 40.6MB → 8.8MB in public/images, 78% saved
Resizing alone had already been done and only got 34% from here; the format change is what got the rest. Anything over 2000px on its longest edge was downscaled first — still ~2× for retina, since nothing on the site displays wider than the 1184 content column. The two PitchPivot video posters were 5600px wide, which is where the single biggest wins came from.
perf
The process-log folder was a second, larger pool nobody was counting — 26.2MB → 6.1MB
31MB of exported process-log screenshots sitting in public/process, referenced by hash-named paths from six static HTML files. It was bigger than the entire project-images folder and had never been through any optimisation pass, because every previous pass had looked at public/images. Worth remembering: "the images" is not a folder, it's a question.
quality
Chose the lossless/lossy split per image by measuring, not by rule of thumb
Going fully lossy saved 87%; the honest version saved 78%. The 3MB difference buys 17 images that are mathematically identical to their source rather than subtly degraded. The ones that needed it are those with large flat areas next to hard edges — raising the quality setting barely helped them (q98 measured essentially the same peak error as q90), so it was lossless or nothing. Verified afterwards that all 13 in the main pool decode with zero error.
gotcha
The social preview image stays a PNG, deliberately
LinkedIn, Slack and several other unfurlers don't reliably render WebP. A social card that fails to load is worse than a large one — and it's the single image most likely to be seen by the people the site is for. It's now the only raster file on the site that isn't WebP.
gotcha
A first attempt at measuring quality reported catastrophic damage that wasn't real
Comparing the transparent PNGs directly showed maximum error on dozens of images — black-to-white pixel differences. The cause was comparing pixels underneath full transparency, which lossy WebP is free to discard because nobody can see them. Compositing both versions over white first dropped the worst real error to 34/255. The measurement was broken, not the images — and the broken version was the one that looked alarming enough to act on.
assets
Replaced a 76MB video with a Vimeo embed
Too big for GitHub Pages in practice and close to the per-file ceiling. Deleting the file doesn't reclaim the weight — it's still in the commit that added it, so every clone still downloads it. That's fixable only by rewriting the branch before it merges, which is a decision with a deadline attached rather than something to do later.
process
Backed the originals up outside the repo before touching anything
Several of the newest images were still untracked, so git was not a safety net for them — an in-place conversion would have been unrecoverable. Worth checking which files are actually tracked before running anything destructive across a folder, rather than assuming version control has it covered.
quality check
Original vs WebP, 1:1 crops — line art and chart labels (top two) survive lossy compression cleanly. The bottom pair is the failure case: the flat black area picks up grey mottling and edge ringing. That third row is why the lossless carve-out exists.
Where the remaining weight is. Of the 47MB built site, ~13MB is video and ~7.5MB is the map and district SVGs plus fonts. The images are no longer the biggest thing.
Shareable hook
I cut my portfolio's build from 106MB to 47MB, and the single biggest pool of weight turned out to be a folder I'd never thought to look in — exported process-log screenshots, larger than every project image on the site combined. The lesson wasn't about compression settings. It was that "have you optimised the images?" quietly means "the images you remember having."
