Type scale & card hierarchy

Getting the portfolio's visual hierarchy to hold up: a real mobile type scale, and card sizing that keeps the project work dominant over the editorial content around it. Also the session where two separate tooling problems stacked and ate an hour.

4 Aug 2026 Type scale, card weight and the spacing floor Building with Claude

Started as a typography pass and turned into a hierarchy pass. The type scale had no mobile end at all, and once that was fixed it became obvious the card sizing had the same problem in a different form: the secondary content was rendering larger than the work it was meant to sit beneath.

1 — The type scale had no mobile end

The check started at desktop, and desktop turned out to be entirely correct — every size, weight and line-height matched Figma. The gap was that the same values were rendering at 402px too. An h1 was 36px on a phone where Figma says 28.

px is what you read off Figma; rem is what actually ships. The two only line up at the browser's default 16px root — which is the point: if a reader has set their browser text larger, every one of these scales with it. The old px scale couldn't respond to that setting at all.

The important finding is in the h2 row: the mobile card title uses Figma's Desktop/h3 style, not a "Mobile/h2". So the mobile scale isn't a shrunk desktop scale — it's a remapping of roles. That's only visible by reading the styles attached to real nodes; it can't be derived by scaling numbers down.

Type
Fluid clamp() per style, anchored on the two real Figma frames (402 and 1622)
Both ends land exactly on a real design value and only the middle interpolates. Breakpoint steps were rejected for the same reason the container padding is a clamp: a step can run the value backwards at the boundary, a clamp can't.
Type
Converted the whole scale from px to rem
px ignores the reader's browser font-size setting entirely — the site literally could not be scaled up by anyone who needs that. The vw term makes it fluid; the rem term is what makes it accessible.
Type
Migrated 10 hardcoded text-[Npx] call sites onto tokens
The plan was "all in the token layer so no call sites change" — which doesn't hold while a third of them opt out. Those elements would have stayed at desktop size on mobile.
Type
Weight stays a separate class at the call site
Figma's text styles bundle size + weight; Tailwind's fontSize can't carry weight. This is the one place the token can't enforce the pairing, so it has to be checked against the style name by hand.
Deliberate divergences from Figma this session — all recorded at the code site so a future sampling pass doesn't silently restore the file's values: h2 desktop 32→28 (card titles read too heavy at wide breakpoints), body-lg line-height 1.5→1.6, button letter-spacing 0→0.02em (bold labels on a filled dark surface), breadcrumb bold→semibold, editorial card widths, AsideCard internal gap. Worth reconciling in the Figma file at some point.

2 — The cards were competing with the work

The brief was that the talks/writing and About cards felt too prominent next to the actual project work. The hypothesis was that they spanned too many grid columns. Measuring showed the effect was real and the mechanism wasn't.

At 1440Card widthMedia
Project cards (3-up)355320 × 278
MediaCards (talks)400400 × 300
AsideCards (About)400 / 600400 × 300

The secondary content was measurably wider than the smallest work cards. But col-span only decides which columns a card's frame occupies — the card is then aligned inside that frame with justify-self and sized by an explicit w-[400px]. Dropping a span would have slid the cards sideways and left them exactly as large.

Cards
Editorial cards 400→320, wide card 600→480
320 sits clearly below the 355 3-up project card and is already a number in the system (the project artwork's own width). The wide card keeps its 1.5× relation so the editorial zone holds its internal hierarchy, and 480 stays under the 562 2-up card.
Cards
Width consolidated into one constant per size
It had been repeated across all seven collage entries. Changing editorial weight is now a one-line edit rather than seven.
Cards
ValueCards pinned to a fixed 278 with auto-fit tracks
They had been sized as a share of the container, so they grew as the viewport narrowed — 278 at desktop, ~430 at tablet, full-bleed on a phone. Backwards. The fixed track reflows 4→3→2→1 on its own with no breakpoints to keep in sync, and resolves to exactly the Figma row at 1184.
Visual worth adding here: a before/after of the Approach ValueCards at a tablet width (~900px), showing them filling the column vs. holding 278. It's the clearest illustration of "the cards got biggest exactly where there was least room."

3 — The proximity floor

Tightening the three About cards took three passes, and the third one hit a real constraint rather than a number that could keep going down.

PassBetween cardsInside a cardWhat happened
Start224 / 6424Uneven — a stagger offset stacked on the row gap, making the first gap 3.5× the second
Second120 / 4024Halving the offset didn't fix the unevenness, only reduced it
Third32 / 3224Offset removed entirely — gaps finally equal
Fourth24 / 2416Floor reached: internal gap had to come down first

The constraint: the gap between two cards has to stay larger than the gap inside one, or proximity stops grouping and it gets ambiguous which caption belongs to which drawing. With the internal gap at Figma's 24, the collage gap couldn't go below 32 without the cards visually merging. Lowering the internal gap to 16 is what made room for 24 between them.

Practical version for next time: when a "bring these closer together" request stops working, check the internal spacing of the thing being moved. The between-gap can only go as low as the within-gap allows, and reducing it past that point doesn't read as tighter — it reads as broken.

4 — Spacing that turned out not to be spacing

Two gaps on the page were mostly made of things that weren't spacing decisions at all.

Map → "Work": 238px

110px of it was the sticky nav, invisible at that scroll position but still holding its full height in layout. 48px was hero padding that read as part of the gap. Only 80px was the actual section padding. Now 80 total, with the nav out of flow.

Podcast card's loose gap

The iframe's own box was flush and exactly 16px from the title — same as every image card. The extra space was inside the Spotify iframe: giving a fixed-height player an aspect-ratio box makes it letterbox itself. Sizing the box to the player (152px) removed it.

Both cases looked like spacing bugs and measured as correct. The lesson is to measure the element's box and the visible content separately — when they disagree, the problem isn't in the spacing system.

5 — Mobile spacing, reversed twice

This one is worth recording because the second decision undoes part of the first, and both were right at the time.

First
Measured the below-xl rhythm off the 402 frame
Those values had been invented. "Figma has no frames between 402 and 1622" had been read as "no frames at all", so the small end was guessed. The 402 frame does specify a rhythm — and notably it isn't uniformly tighter than 1622, so no small-end number can be derived by scaling a desktop one down.
Then
Deliberately overrode the 402 frame and opened mobile back up
On a real phone that rhythm read flat. The ratios showed why: structural gaps had been compressed to 0.40–0.48 of desktop while local ones sat at 0.67–0.75, so a section break came out barely larger than a card gap. Everything now sits on one ~0.7 ratio — the fix was proportional, not a flat increase.

6 — Working with the Figma file

Meta-notes about the file itself, which are the easiest thing to forget by the next project.

WhatWhy it matters
The file key wasn't written down anywhere Only bare node IDs were recorded, so every session had to re-ask for the URL before any Figma work could start. Now in CLAUDE.md.
Some "component sets" contain only the media, not the card MediaCard's Media and AsideCard's Aside are just the image slot — the card composition (title, description, button, gaps) lives in the page frame. Pulling the component set alone gives an incomplete picture.
Export slots differ per component The ValueCard export is the whole bordered 278×262 container; the AsideCard export is artwork only, because that component draws its own rounding. Getting this wrong means either a doubled frame or a missing one.
"Hug" width produces off-ratio assets Two illustrations came in at 403×300 and 401.54×300 against a strict 4:3 slot. Harmless here, but setting a fixed width instead of Hug removes the guesswork.
Some radii are bound to spacing variables AsideCard's medium variant used spaces/24 as a radius and the large one a raw 28px with no token. Three variants, three different radii, two of them not real radius tokens.
NavbarMobile contains no text So there's no mobile type anchor for the nav links or the footer — those two sizes are currently inferred from the pattern every other role follows, not measured. Flagged rather than presented as verified.

7 — Two tooling problems that stacked

The most expensive part of the session, and worth writing down precisely because the symptom pointed at the wrong cause for four rounds.

Problem 1
Tailwind caches its config per Node process
Editing tailwind.config.js never reached a running dev server: the config is resolved once and it's ESM, so it can't be re-imported. Component files hot-reload normally — which is exactly why some changes appeared and others didn't, from the same server.
Problem 2
Two dev servers were holding port 5173 at once
One bound narrowly (no --host), one broadly (with it). Because those aren't literally the same address, the OS allowed both — no "port in use" error — and then routed localhost to the more specific one, which was the older server. Every restart added a correct server that nothing was talking to.
Fix
npm run dev now supervises Vite and respawns it on config change
An in-Vite plugin was tried first and measured: it logged a restart and kept serving the old CSS, because server.restart() reuses the same process. Removed it — a fix that prints "restarting" while doing nothing is worse than no fix.
The diagnostic that was already written down and ignored: lsof -nP -iTCP:5173 -sTCP:LISTEN — more than one line is the answer. This was in the handoff doc the whole time. Ten seconds would have replaced four rounds of "try restarting it."

8 — Debugging note: a bug that doesn't vary isn't a timing bug

Returning from a case study should land the reader back on the card they left from. Getting it to land accurately took three attempts, and the third was diagnosed by a single tell.

AttemptResultCause
Single scroll948px shortHero map (>1MB), card images and two iframes all load after the jump and grow the page underneath it
Poll on a timer940px shortDeclared the target settled during a lull while its iframes were still loading
ResizeObserverExactReacts to the document actually changing size instead of sampling for it

The tell: it landed at the same wrong pixel every single run. A timing bug varies. That pointed at logic, and the logic was a React StrictMode double-invoke — effects run twice in dev, the first run updated the ref the guard depended on, and the second bailed out. The scroll fired from an effect that was immediately torn down.

What I'd do differently

Check the port first

When output looks stale, verify what's actually serving it before changing anything. Reading the served CSS rule directly is faster than reasoning about caches.

Read the code's own comments

The wayfinding colour drift was documented in a comment directly above the offending line — it recorded that Figma showed no orange and the code had overridden it anyway.

Ask what controls a thing before changing it

"Span one less column" was a reasonable guess that would have had no effect. One measurement showed the width came from somewhere else entirely.

Keep handoffs short

The handoff doc had become append-only — every trap recorded, nothing ever deleted. Durable defects belong in their own register; a handoff should be status plus what's next.
