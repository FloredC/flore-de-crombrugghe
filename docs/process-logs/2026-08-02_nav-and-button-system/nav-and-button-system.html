2 Aug 2026 Nav, buttons, Contact section, and Figma-workflow lessons Building with Claude

Started as "build the mobile navbar" and grew into a full audit of every button's states (hover/pressed/focus/selected) across the site, a rebuilt Contact section, and — once enough small misses had stacked up — a direct conversation about why the misses were happening and how to fix the working process itself, not just the bugs.

Product / component decisions
Nav structure
Three distinct nav states, not one component reused loosely: desktop homepage, mobile homepage (closed/open hamburger), and subpage (identical at every width).
Flore was explicit that the subpage nav is a deliberate dead end — "no hamburger menu, no access to the anchors, since it's on a different page" — not a state that was forgotten. Encoding that as a real structural difference (no open/closed concept at all for subpages) rather than a prop that has to be remembered-to-be-ignored.
Buttons
One ButtonLink component for the whole site, variant prop selects the class — not one component per visual treatment.
Every button-state bug found this session (see below) got fixed in exactly one place because of this. The alternative — a bespoke button per usage — would have meant fixing the same hover-color bug four separate times.
Contact section
Email address renders as a full secondary-styled button that copies to clipboard on click, not a mailto link.
Matches the interaction the map's "Say hi" popover already used. Required new shared code (a useCopyToClipboard hook) since a copy action has to be a real <button>, not an <a>, per the project's own tag-follows-behavior rule — but it had to look pixel-identical to the real secondary button, so the styling is imported from the same source rather than duplicated.
NDA cards
NDA project cards (myRIDE, Rega, SAC, SBB) use the outline "secondary" button, not the filled "primary" one every other project card uses.
Caught in review — the real Figma card for Rega showed secondary, but every card had been built with primary. Root-caused by opening the actual instance rather than trusting the abstract component swatch, which happened to be ambiguous about which variant applied where.
Bugs found, and what they actually were
Focus states
The whole site briefly appeared to have zero keyboard-focus states, anywhere.
Real cause was one inline style on the map's hotspot-marker dot silently overriding its focus ring (inline styles always beat stylesheet rules, regardless of specificity). Because hotspot markers are the very first focusable elements in the page's tab order — before the navbar — tabbing from page load hit nothing but broken markers for several presses before ever reaching a working button. The bug's true size was one component; its apparent size, from Flore's seat, was "the entire site." Worth remembering: where a bug sits in the tab/reading order can make it look far more systemic than it is.
Button weight
The Contact button's label silently rendered at font-weight 400 instead of the correct 700.
A conditional in the button component only applied its bold-text class when a variant had no class of its own — which in practice meant never, since every real variant has one. A pure logic bug, invisible from the design side entirely.
Invented hover state
Nav links showed an underline on hover that isn't part of the actual design.
The underline treatment had been copied from a different, only visually-similar Figma component. The real signal: nav links carry an underline only to mark the current section (a static content difference in the Figma file, not a hover effect) — a distinction that only became clear by checking the navbar's own instances directly instead of trusting a state-grid screenshot from a nearby component.
What Flore learned about structuring the Figma file for Claude
  • Name repeating instances by content, not just by component. Every ProjectCard instance was originally named just "ProjectCard" — finding which one was Rega vs. SBB meant opening several. Renaming to ProjectCard — Rega etc. made lookups direct. Confirmed this doesn't cost anything: an instance's link to its main component is tracked separately from its display name, so renaming is purely additive.
  • Duplicate frames drift silently. A full duplicate of the entire page (a scrolling-prototype frame, probably set up to demo scroll behavior) had been sitting alongside the real page and had already diverged from it in at least one place — a font-weight difference on the Contact section's body copy — before it was found and deleted. If a frame like that needs to exist for prototyping, it's worth either deleting it once it's served its purpose or treating it explicitly as "reference only," never as something that could silently answer a lookup instead of the real page.
  • Enumerate a component's full state matrix before building it. Figma's own metadata lists every hover/pressed/focus/selected variant by name. Several of this session's misses came from building against the one state needed for layout and waiting to be told what else was missing, rather than checking the full list up front.
  • Code Connect isn't available yet. Looked like the real long-term answer to "map a Figma component straight to its code" — but it requires a Figma Organization or Enterprise plan, and the current plan is Professional. Worth revisiting only if the plan changes.
Flore's direct question mid-session — "why did this take so long, I thought it'd be the easiest thing" — is worth keeping as a marker. The honest answer was that five genuinely separate tasks had been bundled into one ask, and that a couple of the "simple" fixes (the NDA button variant, specifically) required real archaeology in a large, partially-duplicated Figma file. Naming that plainly, instead of just working faster next time and hoping it doesn't come up again, is probably worth doing whenever it happens again.
Shareable hook
A full duplicate of my homepage had been quietly living in my Figma file — and it had already started disagreeing with the real one before I ever noticed it existed. The lesson wasn't really about Claude reading Figma correctly; it was that a design file needs the same "single source of truth" discipline as a codebase, or the AI reading it will confidently build from whichever copy it finds first.
