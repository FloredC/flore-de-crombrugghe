Chapter navigation & reading progress

Giving the Artifakt case study a way to orient yourself in it — a thin progress line and a floating chapter navigator — without introducing a second navigation that competes with the global one. Three directions explored in Figma, then built, then reshaped repeatedly by looking at it.

28 Aug 2026 Three directions for a chapter nav Figma design

The problem: Artifakt is long enough to lose your place in, but it already has a global nav, and a second persistent navigation risks reading as a competing one. Three placements were drawn against the real page content, each annotated with its own sticky behaviour, active-state treatment and collapse point.

Direction A
Horizontal, below the global nav — a full-width band with a subtle divider, sticky once the hero scrolls out. Collapse to Direction C at ~1024px "when labels begin crowding the global nav."
Direction B
Side / offset, in the left gutter — completely separate from the global nav. Inactive chapters show a number only at 35% opacity; the active one reveals its full label with an accent mark.
Direction C
Collapsed contextual — only the current chapter and a progress fraction, expanding on click. Drawn as the small-screen fallback for both A and B.

What testing them in situ showed

A and B were both dropped onto a real screen of the case study rather than judged as isolated components — which is what settled it.

Rejected
B, on a real screen — the "empty left gutter" isn't empty at every width. The chapter numbers land straight on top of the body copy. The direction depended on a layout condition the page doesn't reliably meet.
Rejected
A, on a real screen — docking a second full-width band directly under a global nav that already floats over the content produces two horizontal bars stacked at the top, both claiming to be the page's navigation.
Placement
Floating capsule, bottom-centre — none of the three as drawn
The exploration's real finding was about vertical position, not layout: anything docked at the top competes with the global nav, and anything in the gutter depends on there being one. Moving it to the bottom of the viewport removed both problems at once — it can't be mistaken for the page's primary nav because the primary nav isn't there.
Labels
Chapter numbers dropped — "Overview", not "01 Overview"
All three directions numbered the chapters, and C leaned on a "03 / 05" fraction. Numbering implies the chapters are a sequence you're expected to complete, which is the wrong promise for a case study someone might read two sections of. The progress line already carries "how far through am I" without asking anyone to count.
Collapse
Direction C survived as the small-screen state
The one part of the exploration that shipped intact. The annotated collapse point (~1024px) didn't — see the build session; it turned out to be a function of the type size, not a fixed width.

30 Aug 2026 Building it — and the four things it dislodged Building with Claude + Figma sync

The nav and progress line themselves took maybe a third of the session. The rest went on things that only became visible because there was now something on screen to look at — the hero's vertical balance, the global navbar's sizing, a silent anchor-scroll bug, and the fact that only one of ten project pages had a real contact section. That ratio is the honest headline.

The build decisions that mattered

Structure
Chapters are navigation vocabulary only — no new headings on the page
Five macro chapters over eleven existing sections. "Making it work" covers four editorial headings and appears nowhere in the writing. The section ids already existed in the content file and were already described there as anchors — they just never reached the DOM. So the nav points at the page's real structure instead of markers added for its benefit.
Scrollspy
Cached offsets in one scroll pass — not IntersectionObserver
IO is the obvious tool and doesn't survive contact. A band meaning "a line" has to be zero-height, and a zero-height root margin intersects nothing. Give it real height and any section taller than the band leaves it empty — the callback stops firing mid-chapter and the nav holds a stale answer.
Landing position
Where a chapter lands lives in CSS; the JS reads it back rather than restating it
scroll-margin-top: clamp(120px, 22svh, 240px) on the anchors, and the scrollspy reads it with getComputedStyle().scrollMarginTop — already resolved to pixels, clamp and svh gone. One place decides the landing; the "which chapter counts as current" line follows it. Two numbers restating the same intent is how they end up disagreeing after someone edits one.
Craft detail
Each label reserves its own semibold width up front
The active chapter is heavier than the inactive ones, and heavier is wider — so every scrollspy change would have visibly reflowed the capsule while the reader was scrolling and not touching it. An invisible bold copy of each label sits behind the visible one and holds the width. Measured identical at 458.97px across all five active states.
Progress line
Completes at the contact block, not at the bottom of the document
Below the article sit the contact block, the prev/next band and the footer — roughly a screen and a half that isn't reading. Counting it would park the bar near 90% for the whole ending, which reads as "you never finish."
Reveal point
Appears as soon as the hero is passed, not at chapter two
The first rule meant a reader passed two whole sections with no sign the page had chapters at all — the control announced itself in the middle of the reading rather than at the door.

The bug worth remembering: a width that changes as you scroll

"Make the menu the same size as the chapter bar" was solved by tying the menu's width to the trigger. That made them equal — and equal to whichever chapter you happened to be reading.

Broken
"Overview" active — a short label makes a narrow trigger, the menu inherits it, and "Back to top" wraps onto two lines. Nothing about the component changed; the reader just scrolled somewhere else.
Fixed
Fixed 250px on both — the two are the same size because they are the same number, and neither moves as you scroll. A width that depends on content you don't control isn't a width.

Four things the nav dislodged

Anchor scroll
Every in-page anchor now scrolls itself instead of relying on the browser's fragment navigation
Reported as "the scroll effect is gone." The CSS was intact — the real cause is that a fragment navigation to where you already are is a no-op. Click "About" → URL becomes /#about. Scroll away by hand. Click "About" again → the browser compares fragments, finds no change, and does nothing. No scroll, no error. It's reached constantly, because "Back to Portfolio" returns you to /#project-<slug> — so that project's map popover CTA is dead before you touch it.
Hero spacing
Top padding retuned on all ten subpages: pt ≈ the nav pill's bottom edge + pb
The diagnosis ("the space between the navbar and hero content is too big") was right, and measuring said why: at 1440×900 the hero drew 200 above and 80 below, but the pill's bottom sits at 85 — so what the eye actually compared was 116px of empty stage against 80. The h1 began at y=426 on a 900px screen, past the halfway line.
Navbar sizing
Pill height is declared, not left to the contents
"Navbars should be the same size across pages" wasn't achievable by matching padding. The homepage pill is sized by a fixed 53px avatar → 70 everywhere. The subpage pill's tallest child is the Contact button, whose height rides the fluid type → 67 / 68 / 70. Same padding, same components, three heights, and nothing in the code said otherwise.
Contact
One shared contact section on all ten subpages, replacing three different endings
Only Artifakt had a real one. PitchPivot and the snapshots ended on a prompt whose CTA navigated to the homepage's contact section; the four NDA pages and the WIP page had nothing. Pointing the nav's Contact button at a signpost would have satisfied the letter of the request and none of it.
Before
Hero, before — 200px above the content, 80 below. The reader's first impression of the page is empty colour.
Before
Navbar, before — a 58px avatar and a 61px Contact button in a 75px pill, after the CTAs elsewhere had already been made smaller. The imbalance is what prompted the whole sizing pass.

What the Figma file taught us

Five design edits arrived mid-session — invert the nav, add chevrons, change the padding, resize mobile, add an accent token. Each meant a re-pull, and the re-pulls kept surfacing the same class of problem. This is the part that transfers to the next project.

What happened Why it bit What to do next time
Detached layers don't follow a component swap After inverting the chapter nav, the collapsed trigger's active underline still bound Colors/Text/text-primary — a black rule on a black pill, invisible. The expanded menu's active label was also still 14px where every sibling had moved to 16. After inverting or restyling a component, check the layers that were detached or overridden — they're the ones that silently keep the old binding. Both were caught by reading the export, not by looking at the frame.
A value with no variable can't be carried across The menu's rim was a raw #a8a8a8 and the progress track a raw #f2f2f0 — neither matches any primitive, so there was nothing to reference and no honest name to give them. If a colour is meant to persist, name it in the file. An unnamed hex arrives in code as either a hardcoded literal or a wrong-but-close token.
An unpublished token can't be read by name The new accent was added as a semantic variable but isn't in a published library and no node binds it yet — so the hex was readable and the name wasn't. It's carried under a placeholder name pending confirmation. Publish variables to a library, or apply the token to at least one node, before asking for it to be used. The value alone doesn't tell code what to call it.
Fixed widths are a mechanism, not a spec The desktop capsule was drawn at a fixed 586px. Our type is fluid (14→16px), so 586 would pin the button right while the labels shrank away from it. Extract what the fixed width buys — here, 60px of air between two groups — rather than the number. Figma later restated it as an explicit gap-32, which confirmed it.
Exports carry preview artefacts and off-system icons The Lottie eye shipped with an opaque white 800×800 backdrop layer. Separately, ic-arrow-up was the only icon painted pure #000000 on stroke rather than #0E0E0E on fill — so alone in the set it couldn't follow its container's colour, and was invisible on the dark pill. Turn preview backdrops off before exporting. Re-exporting the arrow from the same component as the rest of the set deleted a build-config workaround entirely.

Two code decisions worth pointing at

Performance
The eye animation's player is lazy-loaded; the progress bar is a transform
Lottie is 168KB minified against a 477KB bundle — too much to spend up front on a decorative eye, so it sits behind a dynamic import fired when the pipeline section scrolls into view (48KB gzip chunk; main bundle grew 1.2KB). The progress bar moves with scaleX rather than width, so it composites instead of laying out the page on every scroll frame.
A trap
A bug that passed the build and only broke in dev
The Lottie player's default path is a UMD bundle. Rollup's interop gives it a default export at build time — so vite build succeeded — but the dev server serves it raw, where it exports nothing. Silent failure, clean production build. Worth remembering that "it builds" and "it runs" are different claims.
